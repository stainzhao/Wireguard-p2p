# WireGuard P2P v7.0-beta protocol

## Goal

v7.0-beta activates candidate-based direct path probing while preserving the existing relay-first routing model.
The VPS `10.0.0.1/24` route stays usable during all probes. A direct `/32` route is installed only after WireGuard produces a new authenticated handshake on a candidate path.

## Candidate types and priority

```text
lan4       1000   same-LAN private IPv4
host6       900   globally routable IPv6
mapped4     800   PCP/NAT-PMP/UPnP mapping (reserved for v7.1)
observed4   600   IPv4 endpoint observed by VPS
predicted4  400   predicted symmetric-NAT endpoint (reserved for v7.2)
```

Nodes may advertise `lan4`, `host6`, `mapped4`, and `predicted4`. `observed4` is generated by the VPS from the authenticated WireGuard peer state and cannot be claimed by a node.

IPv6 endpoints must use bracket notation:

```text
[2001:db8::1234]:51820
```

## Probe selection

A node builds a bounded probe list from the remote candidate set:

1. `lan4` is considered only when both peers are observed behind the same public IPv4/NAT.
2. `host6` is preferred over normal IPv4 traversal when IPv6 is locally usable.
3. `mapped4` is reserved for explicit gateway mappings.
4. `observed4` is retained as the normal IPv4 hole-punch candidate/fallback candidate.
5. `predicted4` is reserved for later NAT prediction logic.

The list is deduplicated by endpoint, sorted by priority, and capped at five candidates. If capping would remove `observed4`, the implementation keeps one `observed4` candidate as the IPv4 fallback.

## Probe state machine

```text
relay (/24) active
      |
      +-- candidate worker starts
              |
              +-- candidate A: 2 s
              +-- candidate B: 2 s
              +-- ... max 5 candidates
              |
              +-- new authenticated WG handshake
              |       |
              |       +-- learn actual WireGuard endpoint
              |       +-- install peer /32
              |       +-- keepalive -> 25 s
              |
              +-- all fail
                      +-- remove dynamic peer
                      +-- relay remains active
                      +-- 60 s / 120 s / 30 min retry policy
```

During probing, `PersistentKeepalive=1` is used to create a short burst of WireGuard traffic. Established direct paths return to `PersistentKeepalive=25`.

A candidate succeeds only when `latest_handshake` becomes newer than the baseline recorded before that candidate is installed. An old handshake cannot promote a `/32` route.

## Cancellation and network changes

Each peer state contains a generation number. Candidate changes, stale direct paths, peer removal, or program cleanup increment/invalidate the generation. Background workers stop if their generation is no longer current.

A changed candidate signature resets direct-probe cooldown immediately. This allows a laptop changing Wi-Fi/mobile networks or receiving a new IPv6 address to re-evaluate connectivity without waiting for the previous 30-minute hard-NAT cooldown.

## Relay-first invariant

The beta implementation keeps this invariant:

```text
No authenticated new direct handshake -> no dynamic /32 route.
```

Therefore an unsuccessful LAN/IPv6/IPv4 direct test does not interrupt the normal VPS route.

## Rolling compatibility

The following legacy fields remain available:

- `endpoint`
- `endpoint_type`
- `lan_endpoint`
- `lan_ip`
- `listen_port`

`candidates[]` is additive. This permits gradual upgrades of VPS, Linux Agents, and Windows clients.

## Deferred work

v7.0-beta does not yet implement:

- nonce-backed strict replay protection for `/offer` and `/remove`
- session-bound `/remove`
- PCP/NAT-PMP/UPnP discovery and lease renewal
- symmetric-NAT port prediction
- full ICE / userspace WireGuard UDP multiplexing

Those are intentionally separated from the beta path-state-machine change.
